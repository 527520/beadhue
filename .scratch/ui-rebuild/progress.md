## 自主巡检（Loop Engineering）

主会话用 `loop` 技能自唤醒：常驻进程 `tools/loop-watch.py 600` 盯住本会话全部子代理记录（含新派发的），任一结束即输出 `AGENT_LOOP_WAKE_r15`，另每 10 分钟输出一次心跳；进程不退出，醒来的那一轮被截断也不影响下一次唤醒。每次唤醒：按下面的恢复方法巡检 → 处理（续跑 / 验收 / 合并 / 派发）→ 更新本表。只有进程不在了才需要重启它（进程号见 `tools/.loop-pids`）。

**09-24 12:44 起改为回合内等待**：实测后台通知（Task 完成通知、`notify_on_output`）在主会话空闲时都不会开启新回合（11:35、11:36、12:06 三次完成与 6 次心跳都没唤醒）。现在监视器唤醒行带序号（`AGENT_LOOP_WAKE_r15 #N HH:MM:SS`，心跳 15 分钟），主会话在回合内用 `AwaitShell`（监视器的 shell、`pattern` 写 `AGENT_LOOP_WAKE_r15 #<下一个序号> `）等下一条，处理完再等下一条；回合被平台打断后，用户发「继续」时先读监视器终端文件里的最新序号再接着等。

**子代理认证跟着主会话回合走**：12:37–12:43 在一个 12:16 开始的回合里新派发 4 次、续跑 1 次，全部立即报「Authentication error If you are logged in, try logging out and back in.」；12:46 用户发「继续」开启新回合后，12:47 派发立即成功（10:17 的认证错误也是新回合后消失）。所以派发 / 续跑尽量放在回合开头；回合内等到的事件如果需要派发而报认证错误，就把能做的合并 / 验收做完后结束回合，请用户发「继续」。另外回合被用户消息打断时，终端文件会被清掉，新回合要重启监视器。

启动监视器必须用后台 Shell 并带 `notify_on_output`（匹配 `AGENT_LOOP_WAKE_r15`），而且要在能正常结束的回合里启动。10:35 在一个随后因「未付账单」出错的回合里启动的进程，唤醒行照常打印到终端文件，却一次也没唤醒主会话（10:53–11:07 的三次中断空转了约 16 分钟）。巡检时要核对：终端文件里最新的唤醒行之后，主会话是否确实有过回合；没有就重启监视器。

## 恢复方法（主会话被截断后）

1. 看本表与各票头的 `Completion:`；`git log --oneline` 看已提交的票。
2. 「进行中」的票：用 Task `resume` 发一句「继续」试探；返回「currently running」说明仍在跑，不要重复派发。
3. 子代理的完成通知可能不送达：读 `agent-transcripts/<会话>/subagents/<id>.jsonl` 末尾的最终回报与 `turn_ended` 状态。
4. 票 02 完成后：在主工作区 `git merge --no-ff <它的分支>`，解决冲突，跑 typecheck / lint / 受影响测试，再派发票 03。
